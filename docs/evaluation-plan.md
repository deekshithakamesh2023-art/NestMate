# Evaluation plan

## Goal

Compare whether residents and wardens can complete the primary hostel service tasks with the portal more effectively and with fewer errors than the processes they currently use (for example, WhatsApp messages or paper forms). WhatsApp and paper are comparison examples, not confirmed current hostel processes; recruit participants from a hostel that uses those processes and document their actual baseline before testing.

## Participants and sample-size rationale

Recruit **24 participants: 16 hostel residents and 8 wardens or staff who handle resident requests**. Residents exercise complaint, outpass, hostel information, and fee paths; wardens exercise triage. This is a mixed-role formative comparison intended to expose workflow and comprehension problems and produce directional paired observations. The sample is not claimed to be statistically powered to establish a population-level effect, and results should report the actual recruited sample and missing observations. If no 8 wardens can be recruited, report the shortfall and treat warden findings as exploratory rather than silently substituting residents.

Each participant completes the tasks they are eligible for using both the portal and their real current method. Use a counterbalanced order (portal-first for half of each role, current-method-first for the other half) to reduce order effects. Use equivalent fictional scenarios and do not submit real requests or payments.

## Five moderated tasks

1. **Resident — complaint:** report a broken reading-room light under Maintenance, describe its location, submit, and find the resulting status.
2. **Resident — outpass:** request a two-night visit home using dates allowed by the participating hostel, add a reason, and submit. Record whether policy instructions are understood.
3. **Resident — daily services:** find today's lunch menu, leave meal feedback, and request a laundry pickup.
4. **Resident — fees and notices:** locate the current notice about a facility disruption, find the due amount/date in the fee screen, and reach the payment confirmation. Stop before confirming a simulated payment.
5. **Warden — triage:** find a new maintenance request, change its status, assign the facilities team, and save the update.

The task facilitator gives only the scenario, not navigation hints. If a participant requests help or cannot proceed after two minutes, record the task as unsuccessful, provide assistance, and continue only if the participant wants to. The first task is meant to include status tracking so the team can observe whether a submitted request remains discoverable.

## Measures and analysis

Record per task and per method:

- **Unassisted success rate:** tasks completed to the predefined end state without moderator help ÷ attempted tasks. Report numerator, denominator, and percentage, separately by role and task.
- **Time on task:** elapsed seconds from the scenario prompt to the correct end state; record assisted/abandoned tasks separately and report median and range, not only a pooled mean.
- **Error rate:** count observable missteps that could lead to a wrong request, date, status, assignee, or payment action; define severity and count consistently for both methods. Report errors per attempted task and the error taxonomy.
- **System Usability Scale (SUS):** administer the standard 10-item questionnaire after each method; score using the published 0–100 transformation. Report raw distribution and sample size, and do not describe the score as a percentage or as proof of accessibility.
- **Qualitative observations:** capture confusion, workarounds, privacy concerns, terminology mismatches, and reasons for task failure. Do not record resident case details or payment credentials.

Compare paired portal/current-method results descriptively, by role and task; show participant-level paired observations where consent and anonymization allow. Report scenario differences, order, assistance, withdrawals, missing data, and any prototype defects. Do not invent significance, a benchmark, or a success threshold after seeing results. Pre-register any inferential analysis and sample-size/power calculation before a confirmatory study.

## Exit criteria for iteration

An iteration is ready for broader pilot consideration only after the team has reviewed failures and critical errors, confirmed outpass and payment policies with the responsible staff, resolved accessibility findings, and agreed on service ownership for each request type. These are review gates, not measured claims that this prototype already passes them.
